# L-04 Scene Persistence Handoff

- Enhancement ID and user outcome: L-04; add durable, isolated scene storage to Lorethra without changing unrelated records.
- Status: implemented and focused-verified; complete scene authoring remains unavailable until L-05.
- Explicit implementation scope and exclusions: SQLite migration v21 adds stable scene identity and append-only full-payload revisions; branch creation copies each scene's latest revision into the child and records lineage; backup validation requires both scene tables; changed scene revisions block branch promotion until scene-aware promotion is defined. No scene commands, lifecycle/reference validation, scene snapshots, API, UI, asset remapping, data conversion, or schema downgrade were added.
- Evidence and current source paths: `backend/lke/core/database.py` (`SCHEMA_VERSION=21`, `_SCHEMA_V21`); `backend/lke/core/commands.py` (`_snapshot_branch`, promotion guard); `backend/lke/ops/backup.py` (`_REQUIRED_TABLES`); `docs/contracts/SCENE_DOMAIN.md`; `docs/contracts/DATA_MODEL.md`.
- Existing capability versus precise gap: schema v20 already retains branch revisions, adventures pinned to immutable world versions, exact story turns/edits, memories, and context manifests. It had no first-class scene key or revision rows. The new tables store the complete v1 scene contract per scene revision; command-level schema and cross-reference validation is still L-05/L-06 work.
- Proposed journey and acceptance criteria: the eventual command gateway creates a stable branch-local scene, appends immutable revisions for changes, and snapshots exact final state. In L-04, a fork receives the latest parent scene payload at child scene revision 1; the parent remains unchanged, and `lineage` records the parent branch, fork revision, and source scene revision.
- Module ownership and contract changes: `story_scenes` owns stable `(workspace, branch, scene)` identity and adventure ownership. `story_scene_revisions` owns complete immutable versioned contract payloads. Composite foreign keys tie identity, adventure, branch revision, and source revision together; JSON checks enforce scope and version columns; an insert trigger enforces the adventure's pinned world ID/version.
- Canon, workspace, branch, actor and time constraints: the migration creates no scene rows. Scene keys are composite and branch-local; identity and revisions reject updates/deletes. Branch snapshots copy only each scene's latest revision while the parent retains its full history. Scene changes after a child's base revision are rejected by promotion until L-05 adds compatibility-aware behavior. Production scene creation remains gateway-only and is not yet implemented.
- Source provenance, privacy and cloud consent: the full scene payload is stored locally in SQLite with its existing private intent/state fields and source references. This slice adds no provider, cloud transfer, or export surface.
- Migration, backup, rollback and asset recovery: v21 is a forward-only additive migration with no table rewrites or data conversion. Existing v20 records remain intact. Database backup snapshots include the tables, and restore validation requires them. There is no downgrade path; recovery to an older application requires restoring a backup made before migration. Existing scene image targets remain assistant-turn IDs and are not remapped.
- Dependencies and unresolved decisions: L-05 must implement validated lifecycle commands and scene-aware branch promotion. L-06 must validate participants, interactions, and exact reference ownership. L-07 must create immutable reproducible scene snapshots. Scene IDs and stored full-payload revision contracts are stable once written; storage schema evolution must preserve older contract payloads.
- Verification performed, exact results and limitations: Python 3.13.16 focused scene-persistence and migration suites passed 13 tests. The dedicated scene backup/restore test passed separately. The backup test module could not be imported normally in this environment because Pillow is absent; the scene-only test was run with a placeholder `PIL.Image` module because it does not use image operations. These focused checks do not establish the full backend baseline, API/browser behavior, or user-visible scene authoring.
- Next smallest authorized action: implement L-05 validated create/revise/lifecycle commands through the existing command gateway, including scene-aware promotion compatibility and rollback-on-failure coverage.
